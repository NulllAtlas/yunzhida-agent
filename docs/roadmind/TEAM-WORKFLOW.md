# RoadMind · 详细分工与个人任务流程（TEAM-WORKFLOW）

> 版本：v1.2（2026-09-26）
> 目的：把 4 名成员（P1–P4）在 11 天内的任务，按**个人**拆成可执行的具体步骤流。
> 原则：**功能不砍，精度递进** —— 11 天做出功能齐全（含视频识别低精度版）的闭环 + 参赛 PPT；精度优化放到迭代阶段 B。
> 配套：`TEAM-ROLES.md`（职责与 11 天排期表）、`ARCHITECTURE.md`（多智能体架构）、`FEASIBILITY.md`（可行性）。

---

## 全局规则（人人都要遵守）

- **Day 1 上午 10 点前**：四人共同确认两个契约 ——
  1. `scene.json` 字段结构（P3 主导）
  2. API 接口文档（P2 主导）
  3. `judgment.json` / `response.json` 结构（P2+P3）
- 每人每天结束时，在共享文档（如飞书/语雀）回填：
  - 「完成」「卡点」「明日首个任务」
- 所有接口以 mock 数据并联开发，谁都不等谁。
- 每完成一个里程碑（D3/D6/D11），全队 15 分钟验收演示。

# P1 · 队长 / 产品 + 业务

**核心目标**：定义"要判什么、判对算什么"，保证方案贴合交警/车主真实场景，且说得清、能答辩。

### D1 需求与主流程
1. 写出**车主主流程**：打开网页 → 上传行车记录仪视频 → 看到"是否立即需拨 120/122"级联提示 → 应急处置步骤 → 责任预判概览。
2. 写出**交警主流程**：上传/选择案件 → 看责任认定详情（依据+证据）→ 导出认定书草稿。
3. 产出《需求文档 v1》：上述两条流程 + 3 个典型用例（追尾 / 路口抢行 / 车撞行人）。
4. **交付**：`docs/roadmind/REQUIREMENTS.md`

### D2 规则清单 v1
1. 列出 8 类常见事故类型：追尾、变道刮蹭、路口未让行、闯红灯、掉头/转弯未让行、倒车、逆行、车-行/非机动车。
2. 每类写出：**构成要件**（如追尾=后车未保持安全距离）与**责任倾向**。
3. **交付**：`docs/roadmind/RULES.md` v1（表格型：事故类型→要件→法条→责任倾向）

### D3 用例/案例种子
1. 从公开渠道收集 8–12 个典型判例/案例，每例标注：场景 + 责任结论 + 关键法条。
2. 转成 RAG 需要的文本片段（每段 ≤ 200 字，带标签）。
3. **交付**：`docs/roadmind/CASES.md` + `data/cases/*.md`（给 P3 入库）

### D4 评测集 v1
1. 建 10 个评测场景（脚本化输入：场景 JSON 或文字描述 + 期望责任结论）。
2. 命中断言：责任占比、是否引用关键法条、置信度阈值。
3. **交付**：`data/eval/eval_v1.json`（给 P3 调判定）

### D5 应急合规核对
1. 逐条核对应急步骤的合规性（三角牌距离、报警电话、撤离时机）。
2. 产出《应急步骤标准模板》——按事故类型给分步动作 + 紧急度标签。
3. **交付**：`docs/roadmind/RESPONSE-TEMPLATE.md`（给 P3 实现 M4）

### D6 端到端试跑记录
1. 亲自跑一遍全链路（用 P4 的页面），记录 UX 问题与业务口径问题。
2. 整理成《问题清单》给 P2/P3/P4。

### D7 定义评审场景 + 口径
1. 和 P3 对齐"判定口径"：哪些必须判对、哪些可提示低置信。
2. 产出 2 个端到端演示场景剧本。

### D8 评测回归
1. 用 P3 的判定模块跑 `eval_v1`，逐条核对误判。
2. 输出《判定回归报告》→ 反馈 P3 调提示词/规则。

### D9 演示脚本定稿
1. 写 3 段演示台词：① 视频→应急（车主视角）② 视频→责任认定（交警视角）③ 降级场景兜底。
2. **交付**：`docs/roadmind/DEMO-SCRIPT.md`

### D10 全流程彩排
1. 组织 1 次全流程彩排（用真实视频演示集）。
2. 记录卡点，协调收尾。

### D11 答辩定稿
1. 汇总《答辩材料》：背景、价值、架构、演示、差异化、未来。
2. 冻结全部文档，准备装车。

# P2 · 后端 / 架构

**核心目标**：捏合多智能体为一条可调用、可观测的服务链路。

### D1 契约 + 骨架
1. 写 API 接口文档：`POST /upload`、`GET /task/{id}`、`WS /progress`、`GET /result/{id}`。
2. 定义 `judgment.json` / `response.json` / `scene.json` 结构（与 P3 对齐）。
3. 初始化 FastAPI 项目 + LangGraph 依赖：`app/`、`graph/`、`services/`。
4. 用 mock 场景 JSON 建**图骨架**（3 个占位节点：perceive/judge/respond → aggregate）。
5. **交付**：`docs/roadmind/API.md` + 可启动的空服务

### D2 图串通（mock）
1. 让 `perceive`/`judge`/`respond` 三个节点用 mock 数据可完整走一遍并出 `result`。
2. 实现 `POST /upload` 接受文件 + 创建任务状态（pending→processing→done）。
3. 实现 `GET /task/{id}` 状态查询。

### D3 RAG 服务
1. 接 chromadb，写 `index_rules.py`：法条/案例切分→embedding→入库脚本。
2. 写 `retrieve(query, top_k)` 接口，供 judge 节点调用。
3. 接 MoMA LLM 网关：封装统一 `call_llm(messages)`（含鉴权/超时/重试）。
4. **交付**：`services/rag.py` + `services/llm.py`

### D4 判定节点接真 LLM
1. judge 节点：scene + retrieve 结果 → 拼 prompt → LLM → 解析成 `judgment.json` 回填状态。
2. 加超时与解析容错（失败回退规则匹配）。
3. WS 进度推送：processing 阶段给前端发阶段消息。

### D5 应急节点 + 进度
1. respond 节点：scene 画像 → 选模板 → LLM 润色 → `response.json`。
2. 接 WebSocket 全流程进度（上传→感知→检索→判定→应急→完成）。

### D6 全链路无 mock
1. 移除 mock，perceive（调 P3 的服务/接口）→ judge → respond 全走真实数据。
2. 端到端跑通一个视频，输出 result 到前端。
3. 加错误处理：视频解析失败、LLM 超时、空场景。

### D7 API 完善 + 鉴权
1. 补 `POST /register`、`POST /login`、JWT，区分车主/交警角色。
2. API 参数校验、统一错误码、日志。
3. 交警端需要的 `GET /cases`、`GET /case/{id}`、导出草稿接口。

### D8 性能与并发
1. 任务队列（如简单线程池/队列）避免阻塞；限制并发。
2. 大视频分帧处理策略、超时熔断、日志+指标。

### D9 部署
1. 写 `Dockerfile` + `docker-compose.yml`（api + rag + 前端静态）。
2. 写 `README` 启动说明、环境变量（MoMA 地址/密钥/模型名）。
3. 自测：新环境一 yarn/npm + docker compose up 即可跑。

### D10 稳定性 + 文档
1. 全流程稳定性测试，修崩溃点。
2. 写 `deploy/docs/RUNBOOK.md`：如何起、如何换模型、如何加规则。
3. 支持 P1 彩排（负责线上起环境）。

### D11 交付核对
1. 核对交付包：源码、依赖、README、demo 说明。
2. 确认在演示环境可 5 分钟内复现。

# P3 · 算法 / 核心智能

**核心目标**：让系统"看得懂视频、判得清责任、给得出处置"。

### D1 契约 + 检测跑通
1. 定 `scene.json` 结构（字段见 `TEAM-ROLES.md` §5 初版，细化车辆/事件/场景）。
2. 本地装好 YOLO（ultralytics）+ ByteTrack，用 1 段公开行车记录仪视频跑出检测框。
3. 产出《scene JSON Schema v1》。
4. **交付**：`docs/roadmind/SCENE-SCHEMA.md`

### D2 视频→场景可用
1. 实现抽帧 + 检测 + 追踪，输出 `scene.json`（车辆轨迹 t/x/y/speed、事件、场景）。
2. 暴露服务接口 `POST /perceive`（供 P2 调用）。
3. 关键帧提取（碰撞前后 ±1s 的各帧）。

### D3 感知完整
1. 补：车道线/信号灯检测（可先用预训练或规则近似）、事故瞬间识别（速度骤变/重叠）。
2. 输出关键帧图保存，供前端可视化。
3. 提供 `GET /perceive/{id}/keyframes`。

### D4 判定智能体 v1
1. 写 judge 提示词：角色（交警辅助研判）+ 要件清单 + RAG 结果 + scene → 输出 JSON。
2. 实现推理链校验：输出格式解析、非法值兜底。
3. 用 P1 的 `eval_v1` 初测，记录命中率。
4. **交付**：`services/judge.py`

### D5 应急智能体 v1
1. 写 respond：scene → 事故类型画像（追尾/碰撞行人/翻车/起火等）。
2. 规则：紧急度分级（伤亡/起火→最高）；接 P1 的 RESPONSE-TEMPLATE。
3. 输出 `response.json`。
4. **交付**：`services/respond.py`

### D6 闭环修整
1. 全链路接真实数据（P2 集成），修判定/应急边界（认不出车/夜间/遮挡）。
2. 和 P1 对齐判定口径，调提示词。

### D7 判定结构化
1. 判定理由结构化：`reasoning` 分条（如 ["A 未让行直行车辆","B 超速"]）。
2. 责任书草稿文本生成（交警端导出用，配合 P4）。

### D8 评测调优
1. 跑 `eval_v1` 全量，按 P1 回归报告调提示词/规则/阈值。
2. 目标：10 场景中至少 8 个责任结论正确或"低置信提示"兜底。
3. 补：置信度校准（拿不准就标低置信 + 提示人工复核）。

### D9 异常容错
1. 处理：无有效车检测、模糊/夜间/遮挡、多车复杂场景（MVP 阶段目标是"能识别基本要素"）。
2. 降级路径：感知置信低 → 返回"需补录"，联调 P4 的文字补录表单，自动转文字描述输入。
3. 输出场景置信度 `scene.confidence`，供前端提示。

### D10 降级链路完备
1. 保证"识别不出即自动转文字/照片补录"链路稳定，任何输入都能出完整结果。
2. 记录 MVP 精度基线（识别对车/人/基本要素即可），作为迭代阶段 B 的优化起点。

### D11 演示确认
1. 用最终演示视频集（P1 提供）跑通，确认 3 个场景全部出结果。
2. 冻结算法版本，写算法说明（给答辩 + PPT）。

# P4 · 前端 / 全栈

**核心目标**：让车主和交警都"看得懂、用得顺"，并把智能体过程可视化为说服力。

### D1 骨架 + 类型
1. 建前端工程（Vue3 + Vite 或 React），配路由：`/owner`、`/police`、`/login`。
2. 用 P2 的 API 文档生成 TS 类型（scene/judgment/response）。
3. 先出静态页面骨架 + 假数据渲染。

### D2 双端页面（mock）
1. 车主端：上传区、进度条、结果卡片、应急步骤列表。
2. 交警端：案件列表、责任认定详情占位。
3. 用 mock JSON 先能显示"判定结果 + 应急步骤"。

### D3 视频可视化
1. 视频播放 + 检测框叠加组件（读 `scene` 的轨迹/关键帧）。
2. 时间轴：拖动回放关键帧 / 检测框。
3. **交付**：视频可视化组件 demo。

### D4 车主端联调
1. 接真实 API：上传 → 轮询任务状态 → 完成后拉 result。
2. 事故时"立即处置"强提示（红色弹层，如撞人→拨 120）。
3. 应急步骤高亮展示 + 保险报案指引。

### D5 车主端完成
1. 应急步骤分步引导（勾选完成）、责任预判概览卡片（含置信度）。
2. 移动端适配（行车记录仪事故场景车主常用手机）。

### D6 交警端详细页
1. 案件列表 + 点击进详情：责任认定（占比 70/30）、法条依据、理由分条。
2. 检测可视化嵌入（调 P3 的关键帧接口）。

### D7 交警端完整
1. 证据清单可视化（关键帧 + 检测框 + 事件时间戳）。
2. 认定书草稿：排版 + 导出（PDF/截图）。
3. 角色权限：登录后按角色显示对应端。

### D8 打磨 + 回放
1. 关键帧回放完善、时间轴交互优化。
2. 移动端 + 桌面端适配与细节打磨（loading/空态/错误态）。

### D9 降级 UI + 打磨
1. 文字补录表单（当感知降级时，车主/交警手动填现场要素）。
2. 从表单数据触发判定（调 judge 接口），保证"无视频也能用"。

### D10 录屏 + 素材
1. 录制 3 段演示视频（配合 P1 脚本）。
2. 整理上架/答辩素材：截图、UI 说明。

### D11 最终成品
1. 最终演示录屏、修最后 UI 问题。
2. 交付演示用的独立页面（减少现场网络依赖，预置 demo 数据）。

## 风险提醒（原则：功能不砍、精度递进）

- **MVP 视频感知精度可低，但功能必须保留**：即使识别不准（夜间/遮挡），也要走通"视频→场景→判定→应急 → 前端"的完整链路；识别不稳时自动回调"文字/照片补录"，保证任何输入都能出完整结果。
- **判定永不承诺 100%**：输出置信度 + 理由，标注"辅助建议"。
- **精度是迭代目标**：MVP 先保证"功能齐全 + 能演示"，精度（轨迹重建、夜间/遮挡识别、置信评估）统一归入迭代阶段 B。
- 每个里程碑先保"功能完整、能演示"，再谈"更准"。
